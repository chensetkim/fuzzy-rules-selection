# `CARS/rule_selection_real/` — what's in each folder

Output of the **flat** (single 7-input engine) NSGA-II rule selection run on the
real `Data/csv` corpus. The hierarchical counterpart lives in
`T-HFIS/rule_selection_real/` with the same three-folder layout.

The three folders are **the same selection pipeline run under three different
train/test splits**. They are not three alternative rule bases to pick from:
only `primary/` is meant to be deployed; the other two exist to tell you whether
`primary/`'s numbers can be trusted. See `Data/RULE_SELECTION_RESULTS.md` §2 for
the methodology and `CARS/fuzzy_rules_selection.md` §3.4/§10/§11 for why the
extra two splits were needed.

---

## `primary/` — the deployed rule base

Scenario-stratified 70/30 random split (`stratified_scenario_split`,
[`Data/real_data.py:153`](../../Data/real_data.py#L153)): all six attack
variants and every env/round/atkcount appear on both sides. This is the only
folder trained on the full corpus, and the only one you should ship from.

| rules | test F1 | FPR | recall | precision | expert overlap |
|---|---|---|---|---|---|
| 15 | 0.9153 | 0.0061 | 0.8628 | 0.9747 | 1/18 (Jaccard 0.031) |

Generated by `CARS/rs/run_real_selection.py` (pop 150, gens 250, 40k-row
stratified training subsample for the search; metrics on the full split).

## `round_holdout/` — generalisation to an unseen simulation repetition

Trains on mobile r1+r2 + static r1, tests on mobile r3
(`round_holdout_split`, [`Data/real_data.py:171`](../../Data/real_data.py#L171)).
This is a **full independent re-run** of candidate generation, MF fitting and
NSGA-II — r3 is never touched during selection, so it is a genuinely fresh
random realisation of every scenario.

| rules | test F1 | FPR | recall | precision | expert overlap |
|---|---|---|---|---|---|
| 15 | 0.8317 | 0.0038 | 0.7239 | 0.9774 | 0/18 (Jaccard 0.000) |

**Reading:** F1 drops 0.084 vs primary, all of it recall (precision actually
rises). A modest gap like this means the primary number is not pure split
leakage. Not deployed.

## `loso/` — generalisation to an unseen *attack type*

Six subfolders `S1`…`S6`. For each fold, train on the other five attack types
(every env/round/atkcount) and test on the held-out one
(`scenario_holdout_split`, [`Data/real_data.py:180`](../../Data/real_data.py#L180)).
This addresses the leakage the design docs flag: consecutive rows from the same
run are autocorrelated, so a random split inflates the test score; holding out a
whole attack type removes that.

| fold | rules | test F1 | FPR | recall | precision | expert overlap |
|---|---|---|---|---|---|---|
| S1 | 13 | 0.7943 | 0.0072 | 0.6713 | 0.9725 | 1/18 |
| S2 | 12 | 0.6944 | 0.0054 | 0.5416 | 0.9674 | 0/18 |
| S3 | 16 | 0.9756 | 0.0037 | 0.9623 | 0.9893 | 2/18 |
| S4 | 12 | 0.9244 | 0.0072 | 0.8948 | 0.9559 | 0/18 |
| S5 | 19 | 0.9754 | 0.0082 | 0.9902 | 0.9610 | 0/18 |
| S6 | 12 | 0.6513 | 0.0066 | 0.4967 | 0.9460 | 0/18 |

Mean F1 0.836, but the spread is the point: **S2 and S6 collapse** (0.69 / 0.65)
while S3–S5 hold above 0.92. Precision stays ~0.95–0.99 everywhere — the failure
mode is always missed detections, never false alarms. So the rule base
generalises well to fresh repetitions of *known* attack types but poorly to
*unfamiliar* ones. State this as a limitation; it is not a reason to select a
different folder's rules.

Run by `CARS/rs/run_loso.py` at reduced pop 80 / gens 120 — this is a
6-fold validation sweep, not the deployed-rule search, so its rule bases are
not comparable head-to-head with `primary/`.

## Files in each folder

| file | contents |
|---|---|
| `selected_rules.txt` | knee-point rule base, human-readable (antecedents, consequent, support, confidence) |
| `selected_rules.c` | same base exported as generated C for the firmware |
| `selected_rules_best_f1.txt` / `.c` | max-F1 solution instead of the knee point |
| `pareto_front.csv` | the full NSGA-II front (one row per non-dominated base, with metrics and rule list) |
| `overlap_report.txt` | per-front-member agreement with the 18-rule expert base |

The `loso/S*/` subfolders omit the `best_f1` variants.

**Knee vs best-F1:** default to `selected_rules.c` (knee point) — it is the
accuracy/compactness tradeoff point the front is selected on, and it is what the
metrics quoted above refer to. Switch to `selected_rules_best_f1.c` only if rule
count genuinely doesn't matter for the deployment.

All bases satisfy the hard NSGA-II constraint `12 ≤ |rules| ≤ 29`; F1/FPR are
measured at `AC ≥ 65` (the firmware's `FUZZRID_TAU_Q_PCT`).

---

## Caveat on the expert-overlap column

`jaccard` here is |selected ∩ expert| / |selected ∪ expert| over pool indices
([`CARS/rs/report.py:30`](../rs/report.py#L30)). It is fine for comparing
members of the same Pareto front, but **do not compare it against the
T-HFIS Jaccard** — the two pipelines have very different expert densities in
their candidate pools (flat: 18 experts in 702 candidates, 2.6%; hierarchical:
25 in 78, 32%), so the hierarchical numbers are inflated by base rate alone.

Against a hypergeometric null, the flat primary base keeps 1 expert rule where
0.38 is expected at random (P(≥1) = 0.33) — i.e. **not distinguishable from
chance**. Any interpretability claim should rest on the rules themselves, not on
this number.
