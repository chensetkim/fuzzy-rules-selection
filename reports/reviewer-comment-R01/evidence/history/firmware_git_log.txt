    rpl-mrhof: optional Zero-Cost Link fix (RPL_CONF_MRHOF_ZERO_LINK_FIX)
    
    Stock Contiki 3.0 MRHOF bug: a neighbour entry that is evicted and
    re-created (mobility, NUD) is zero-filled by nbr_table, but a surviving
    parent keeps RPL_PARENT_FLAG_LINK_METRIC_VALID. MRHOF then uses
    link_metric = 0 - a free link: the node advertises its parent's rank and
    the free link wins parent selection, causing spurious parent switches,
    Trickle resets and DAOs (more control traffic, collisions, delay, energy).
    
    New switch RPL_CONF_MRHOF_ZERO_LINK_FIX (default 0 = stock behaviour):
    when 1, link_metric() re-seeds a metric below ETX 1 to the initial ETX 2
    and drops the stale flag. (In DM-2H-FuzzRID the same guard was already
    compiled with WITH_2HOP_TLV; it is now also available without the TLV.)
    
    Verified: with the switch off, clean firmware images are byte-identical
    to design-bundle-v2; with it on, only best_parent, calculate_path_metric,
    calculate_rank and neighbor_link_callback change. Used for the attack-free
    (clean) reference builds of design-bundle-v3.
    Details: Simulation-phD-Project-01/Report/track.md (Problem 2
    "Zero-Cost Link") and Debug/investigation-report.md.

    mspsim: recompute PxIV on IE write (fixes mote freeze / Port-1 IRQ livelock)
    
    IOPort.writePort() case IE updated the CPU interrupt request but did not
    call updateIV(). If a pin flag was set while its IE bit was off (e.g. a
    CC2420 FIFOP edge during CC2420_DISABLE_FIFOP_INT), iv was computed as 0;
    re-enabling IE then raised the Port-1 interrupt with PxIV still 0. The
    exp5438 FIFOP handler reads P1IV (=0, so nothing is cleared), skips
    cc2420_interrupt() and returns, and the CPU re-enters it forever: the mote
    never runs main() again (no log, no radio). Real MSP430 hardware computes
    PxIV live, so this is an emulator bug.
    
    Effect on the design simulations: 17-37% (25-node) and ~64% (50-node) of
    motes froze in mobile runs, biasing every network metric. Verified fix on
    1-1-45-5-100-S1 clean mobile, 3 seeds: frozen motes 32 -> 0, PDR 66.4% ->
    38.6%, delay x4.1, control x2.6, energy x2.3.
    
    Changes: IOPort.java (IE case calls updateIV(), which recomputes iv and
    then calls cpu.flagInterrupt with the same condition as before), and the
    same class rebuilt into tools/mspsim/mspsim.jar and
    tools/cooja/apps/mspsim/lib/mspsim.jar. The unmodified source compiles to
    bytecode identical to the jar it replaces; the patch changes only this call.
    
    Details: Simulation-phD-Project-01/Debug/investigation-report.md
    (Conclusion) and Report/track.md.

    Replace javax.xml.bind with java.util.Base64 in ContikiEEPROM
    
    javax.xml.bind.DatatypeConverter lives in the java.xml.bind module, which
    was removed from the JDK in Java 11. It was the only use of that package
    in the tree, and the only thing pinning Cooja to a Java 8 toolchain --
    a clone on a Java 11 machine failed to compile at all.
    
    java.util.Base64 has been in the JDK since Java 8, so the tree now builds
    under both. Verified with a full clean build on Java 8 and Java 11.
    
    The MIME decoder is used rather than the basic one because
    parseBase64Binary() tolerated whitespace and line breaks; .csc files saved
    by older builds may contain them and the basic decoder would reject those.
    Encoder output is unchanged (standard base64, no line breaks), so saved
    simulations round-trip in both directions.

    Fix ant clean in mobility app; rebuild mspsim.jar for Java 8
    
    Two build breakages surfaced by running "ant clean" for the first time.
    
    apps/mobility was the only app gating init on check_jar, and clean
    depends on init. Cooja's own clean deletes dist/cooja.jar before
    recursing into the apps, so the guard always tripped and "ant clean"
    could never complete. Move check_jar onto compile, where the jar is
    actually needed; clean no longer touches it.
    
    Both committed copies of mspsim.jar held Java 11 (class version 55)
    bytecode, while the toolchain this tree builds with is Java 8 (javac 8
    cannot read 55.0, and Contiki's ContikiEEPROM.java cannot compile on 11
    since javax.xml.bind was removed). The mismatch stayed hidden because
    apps/mspsim/build/*.class were committed and never recompiled, and
    tools/mspsim/build/*.class survived cooja's clean and were merely
    re-jarred. Rebuilt from source under Java 8; every jar in the tree is
    now uniformly class version 52.

    Fix orphaned Cooja progress dialog on fast simulation load
    
    progressDialog.dispose() was guarded by isDisplayable(), a check-then-act
    race against the setVisible(true) that doLoadConfig() leaves queued on the
    EDT. When loading finishes before the EDT realises the dialog -- i.e. any
    load whose firmware is already compiled -- the guard reads false, the
    dispose is skipped, and the EDT then shows a modal dialog nothing can
    close. Abort was dead too, being gated on a loader thread that had exited.
    
    Queue the dispose via EventQueue.invokeLater so FIFO ordering places it
    after the queued show in every interleaving. Same fix in
    reloadCurrentSimulation(), which additionally had no try/finally at all,
    and both Abort buttons now dispose unconditionally.
    
    Documented as rev 2.9 in Report/REPORT-updatation-track.md.
